# Seeding attendance test data

How to put known attendance rows into the `timetracking` schema so the
statistic API has something to compute. Two tables only:
`att_work_sessions` and `att_user_leave_days`. Monthly statistics are
**not** seeded — `POST /attendance/statistic/tenant/{tenantId}` computes
`att_month_statistic` on demand.

Users themselves live in the `accounting` schema and are **not** created
here. Create them through Accounting first (see `manual-testing.md`), then
seed their attendance.

## The two files

| File | What it is |
| --- | --- |
| `sql/seed_attendance_test_data_plain.sql` | Plain `INSERT … VALUES` for tenant 4, users 10 and 20. Every date spelled out; readable as-is. |
| `sql/seed_attendance_function.sql` | Installs `timetracking.seed_user_attendance(...)`, which generates the same shape for any tenant/user. No data of its own. |

Use the plain file to see exactly what lands. Use the function for every
user after that.

---

## Before you start

Both tables use `id integer GENERATED BY DEFAULT AS IDENTITY`, so **never
supply an `id`** — Hibernate owns the sequence and an explicit id will
collide with the next row the app writes.

Connect as the **superuser** `postgres`. The service accounts
(`timetracking_user`) have rights on their own schema but `CREATE FUNCTION`
is cleaner as `postgres`, and inside the container `-U postgres` needs no
password.

---

## Applying on Kubernetes

The pods run in namespace `attendance`, which kubectl is already pointed at.

```bash
kubectl get pod -l app=postgres
```

Then pipe the file into psql **inside** the pod. The `-i` flag is the whole
trick: it feeds a file from your machine to a process in the cluster, so
there is no `kubectl cp` step.

```bash
cd ~/IdeaProjects/attendance-project-common
POD=$(kubectl get pod -l app=postgres -o jsonpath='{.items[0].metadata.name}')

kubectl exec -i "$POD" -- psql -U postgres -d attendance -v ON_ERROR_STOP=1 \
  < sql/seed_attendance_test_data_plain.sql
```

Expected output, for two users:

```
DELETE 0
DELETE 0
INSERT 0 75
INSERT 0 21
DELETE 0
DELETE 0
INSERT 0 75
INSERT 0 21
```

`DELETE 0` means that user had no rows in the window yet — correct on a
first run, and a non-zero count simply means the file replaced what was
there. `ON_ERROR_STOP=1` matters: without it psql keeps going after a
failed statement and reports success.

## Applying on docker-compose

Same file, same idea:

```bash
cd ~/IdeaProjects/attendance-project-common
docker compose exec -T postgres psql -U postgres -d attendance -v ON_ERROR_STOP=1 \
  < sql/seed_attendance_test_data_plain.sql
```

`-T` disables TTY allocation, which is what lets the redirect work.

## Dry run first

Wrap anything in a transaction you then roll back. The rows are inserted,
the summary prints, and the database is left untouched — safe to do against
a live stack:

```bash
{ echo "BEGIN;"; cat sql/seed_attendance_test_data_plain.sql; echo "ROLLBACK;"; } \
  | kubectl exec -i "$POD" -- psql -U postgres -d attendance -v ON_ERROR_STOP=1
```

## What the plain file contains

Tenant 4, six months ending in the current month (2026-05 … 2026-10), on
**business days only**: the first N weekdays of each month are worked days,
the next M are leave days. Leave alternates vacation 1.0 / sick 1.0.

| Month | Worked days | user 10 minutes (7h) | user 10 overtime | user 20 minutes (9h) | user 20 overtime | Leave days | Vacation | Sick |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-05 | 10 | 4200 | 0 | 5400 | 600 | 1 | 1 | 0 |
| 2026-06 | 11 | 4620 | 0 | 5940 | 660 | 2 | 1 | 1 |
| 2026-07 | 12 | 5040 | 0 | 6480 | 720 | 3 | 2 | 1 |
| 2026-08 | 13 | 5460 | 0 | 7020 | 780 | 4 | 2 | 2 |
| 2026-09 | 14 | 5880 | 0 | 7560 | 840 | 5 | 3 | 2 |
| 2026-10 | 15 | 6300 | 0 | 8100 | 900 | 6 | 3 | 3 |

Those are the expected values for API assertions. Overtime is minutes
beyond 480 per day, summed per day — which is why 7-hour days give zero and
9-hour days give 60 minutes each.

Sessions open at 09:00 UTC and close at 09:00 + the day length. All
sessions are closed: an open session (`close_session_date IS NULL`) makes
the read strategies reject the range, so seeded data must never leave one
behind.

October is the current month, and 15 worked + 6 leave days need 21
weekdays, so those rows run to 2026-10-29 — **into the future**. Harmless
for range queries, but pass `p_anchor_month => '2026-09-01'` to the
function if you want the whole window in the past.

## Generating data for another user

Install the function once:

```bash
kubectl exec -i "$POD" -- psql -U postgres -d attendance -v ON_ERROR_STOP=1 \
  < sql/seed_attendance_function.sql
```

Output is just `CREATE FUNCTION`; no rows are written. After that each user
is one line, and the call prints a per-month summary of what it created:

```bash
kubectl exec "$POD" -- psql -U postgres -d attendance -c \
  "SELECT * FROM timetracking.seed_user_attendance(p_tenant_id => 4, p_user_id => 30);"
```

### Parameters

| Parameter | Default | Meaning |
| --- | --- | --- |
| `p_tenant_id` | — | required |
| `p_user_id` | — | required |
| `p_work_hours` | 7 | session length; > 8 produces overtime |
| `p_months` | 6 | window length, ending at `p_anchor_month` |
| `p_worked_days_base` | 10 | worked days in the oldest month |
| `p_worked_days_step` | 1 | added per later month |
| `p_leave_days_base` | 1 | leave days in the oldest month |
| `p_leave_days_step` | 1 | added per later month |
| `p_anchor_month` | current month | the **newest** month of the window |
| `p_day_start` | `09:00` | session open time |
| `p_time_zone` | `UTC` | zone the open/close times are anchored in |
| `p_updated_by` | `seed_user_attendance` | written to `updated_by` |
| `p_replace` | `true` | delete that user's rows in the window first |

Anything omitted keeps its default:

```sql
SELECT * FROM timetracking.seed_user_attendance(p_tenant_id => 4, p_user_id => 31, p_work_hours => 9);
SELECT * FROM timetracking.seed_user_attendance(p_tenant_id => 4, p_user_id => 32, p_months => 3,
                                                p_worked_days_base => 20, p_worked_days_step => 2);
SELECT * FROM timetracking.seed_user_attendance(p_tenant_id => 7, p_user_id => 100);
```

The function raises an exception rather than spilling data when a month
cannot hold the requested days — 21 weekdays is the practical ceiling for
`worked + leave` in a single month.

### Re-running

`p_replace => true` deletes that tenant+user's rows **inside the window**
and re-inserts them: same data, new ids, no duplicates. It touches no other
user and nothing outside the window. Pass `p_replace => false` to layer onto
rows that are already there; leave days then merge on the
`uq_att_user_leave_days` constraint instead of failing.

Which path wrote a row is visible in `updated_by`: `seed_plain` for the
plain file, `seed_user_attendance` for the function.

## Verifying

```bash
kubectl exec "$POD" -- psql -U postgres -d attendance -c \
  "SELECT user_id, to_char(work_date,'YYYY-MM') AS month, count(*) AS worked_days,
          sum(extract(epoch FROM (close_session_date-open_session_date))/60)::int AS minutes,
          sum(greatest(extract(epoch FROM (close_session_date-open_session_date))/60-480,0))::int AS overtime
     FROM timetracking.att_work_sessions WHERE tenant_id=4 GROUP BY 1,2 ORDER BY 1,2;"

kubectl exec "$POD" -- psql -U postgres -d attendance -c \
  "SELECT user_id, to_char(leave_date,'YYYY-MM') AS month, count(*) AS leave_days,
          coalesce(sum(vacation_amount),0) AS vac, coalesce(sum(sick_amount),0) AS sick
     FROM timetracking.att_user_leave_days WHERE tenant_id=4 GROUP BY 1,2 ORDER BY 1,2;"
```

Then call the API with an admin token, one month per request:

```
POST /attendance/statistic/tenant/4?targetMonth=2026-09&idUser=10
```

`targetMonth` is required; `idUser` is optional (omit it for the whole
tenant) and `report=true` additionally publishes to `att.month-statistic`,
whose enrichment consumer reads up to 7 months of history — so a 6-month
window fits in one event.

---

## Removing seeded data

```sql
DELETE FROM timetracking.att_work_sessions  WHERE tenant_id = 4 AND user_id IN (10, 20);
DELETE FROM timetracking.att_user_leave_days WHERE tenant_id = 4 AND user_id IN (10, 20);
```

`att_month_statistic` rows persisted by an earlier statistic call are not
removed by that; delete them by `tenant_id` + `user_id` too if a stale month
shows up in a response.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `relation "timetracking.att_work_sessions" does not exist` | TimeTracking never started against this DB — Hibernate `ddl-auto=update` creates the tables on first boot |
| `permission denied for schema timetracking` | connected as `accounting_user` or another service account; use `-U postgres` |
| `duplicate key value violates unique constraint "uq_att_user_leave_days"` | the plain file was applied twice with the `DELETE` lines removed |
| `no unique or exclusion constraint matching the ON CONFLICT specification` | `uq_att_user_leave_days` is missing; check with `\d timetracking.att_user_leave_days` |
| statistic response shows zeros | wrong `targetMonth`, wrong tenant, or an open session in range making the read strategy reject it |
| `the input device is not a TTY` | add `-T` to `docker compose exec` (or `-i` to `kubectl exec`) when redirecting a file |
